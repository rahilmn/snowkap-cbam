# Authorization matrix

The "permanent net" master plan §38 (P10) calls for: one row per
application-layer service action, the role/capability it actually
requires **in the code today**, and a pointer to the test that proves
the gate holds. This document is generated by reading the code, not the
other way around — if a row here stops matching `grep`, the row is
wrong, not the code.

Produced by the P10 capability-matrix enforcement audit (master plan
§14/§38: "capability-matrix enforcement audit — every service × role ×
capability tested"). See the end of this document for the audit's
findings: gaps found and fixed, gaps found and only reported, and two
places where the gate is real but lives outside the service function
itself.

## Legend

- **Role** — the §14 roles matrix tier a caller needs: `OWNER`,
  `ADMIN+` (ADMIN or OWNER, via `hasAdminAccess`), or `MEMBER+` (any
  active member — day-to-day data entry and reads, §14's default).
- **Capability** — whether the service checks `org.capabilities`
  (`IMPORTER_DECLARANT` / `PRODUCER_OPERATOR`) before acting. As of
  this audit: **nothing does** — see "Capability enforcement" below.
- **Enforcement point** — where in the code the role check actually
  executes. Most services check inside the application-layer function
  itself (Wall 1, `hasAdminAccess(context)`); a few rely entirely on a
  Postgres RLS policy (Wall 2 only, no Wall 1 check exists because the
  function never receives a role at all); two live in a Next.js
  Server Action / Server Component instead of the application service.
- **Proof** — the test file/case that currently exercises the gate. A
  row with no test either lists the gap this audit closed, or is
  flagged in the findings section below.

## Capability enforcement (master plan §14: "Every server action
re-derives membership/role/capability server-side")

**Finding: `org.capabilities` (`IMPORTER_DECLARANT` /
`PRODUCER_OPERATOR`) is not checked anywhere at the service layer or in
RLS. The only place it is consulted at all is
`deriveExperience` in `components/shell/app-shell.tsx:49`, which picks
which nav (importer vs. producer) to render — a UI convenience, not an
authorization boundary.**

Confirmed by exhaustive search, not inference:

- `hasCapability(...)` (`src/application/organizations/org-context.ts:49`)
  is called **only** from its own unit test
  (`org-context.test.ts`) — zero call sites in any application service
  or `app/**` route/action.
- No RLS policy in any migration under `supabase/migrations/` filters
  on `organizations.capabilities`. Every occurrence of the string
  "capabilit" in a migration is either the generic English word (what a
  policy "can do") or genuinely about the append-only-in-MVP write
  policy on the `capabilities` column itself, never a read-side check
  gating access to a *different* table by which capability the caller's
  org holds.
- No `layout.tsx` exists for `app/(importer)/` or `app/(producer)/` to
  redirect a caller whose org lacks the matching capability away from
  the other experience's routes.

Concretely: a MEMBER of an org whose `capabilities` is
`["PRODUCER_OPERATOR"]` only, who directly submits
`createShipmentAction` (an importer-only workflow — e.g. by POSTing the
form action directly, or once any UI surface ever links there for a
dual-capability org), reaches `createShipment`
(`src/application/shipments/create-shipment.ts:51`) with nothing
checking `IMPORTER_DECLARANT` anywhere between the request and the
`insert`. The same is true of `calculateLine`
(`src/application/calculations/calculate-line.ts:134`), `addLine`
(`src/application/shipments/manage-lines.ts:225`), and every other
importer- or producer-flavored service — none of them take an
`OrgContext` today (most take a bare `orgId`), so there is no
capability *available* to check even where a call site wanted to.

This is a real, load-bearing gap in the "two walls, always both"
posture master plan §10 states for org identity and role — capability
gets neither wall. It is **broad, not narrow**: closing it properly
means threading `OrgContext` (not just `orgId`) through every
capability-flavored service and adding a `hasCapability` check to each,
which is a cross-cutting signature change across ~10 files, not a
single fix. Per this audit's own scope (P10, "audit and close real
gaps," not a sweeping retrofit), this is reported here rather than
fixed. It is a strong candidate for the P10/P11 hardening pass — see
master plan §38's "matrix is the permanent net" framing: the matrix
above should grow a non-empty capability column once this lands.

## Findings — gaps found and fixed

1. **`transitionShipmentStatus`'s `LOCK` action had no *application-
   layer* role check.** Master plan §27 screen 12 is explicit —
   "Shipment detail... MEMBER+ (lock ADMIN+)" — and §14's roles matrix
   names "shipment LOCK/declare (importer)" as an ADMIN-tier action.
   The code let any MEMBER click "Lock" on the shipment detail screen
   (`app/(importer)/shipments/[id]/transition-actions.tsx:38`) with
   nothing in `transitionShipmentStatus` itself stopping them — a
   missing Wall 1 (master plan §10's "two walls, always both"). Fixed
   by adding `hasAdminAccess(context)` for the `LOCK` action
   specifically (not `MARK_READY`/`REOPEN`/`VOID`, which §14 does not
   narrow) — `src/application/shipments/transition-shipment.ts:87` —
   and adding the `"LOCK role gate"` describe block to
   `transition-shipment.test.ts` (MEMBER denied without touching the
   database; ADMIN and OWNER both succeed; a regression test locking in
   that VOID/MARK_READY/REOPEN stay MEMBER+).

   **Correction (P10 mandatory authorization review, finding #3,
   2026-08-29):** this entry originally also claimed Wall 2 (RLS) was
   missing — false. `supabase/migrations/20260829090000_p4_shipment_tenancy_hardening.sql:152-158`
   has gated `shipments` UPDATE on
   `status <> 'LOCKED' or app.user_is_admin_or_owner_of(org_id)` since
   P4, and that migration's own header (lines 125-140) is titled
   *"LOCK: ADMIN/OWNER-only, matching §14's roles matrix."* Live-
   confirmed: a plain MEMBER's `update shipments set status='LOCKED'`
   was already rejected by RLS before this audit ran. The Wall-1 fix
   above is still correct and worth keeping (it turns a raw RLS 42501
   into a clean `PERMISSION_DENIED`, and closes a genuinely *missing*
   wall, not an *open* one) — but the finding was narrower than first
   reported, and a matrix that overstates the hole it found is as
   unreliable as one that misses one.
2. **`inviteMember`/`revokeInvitation`'s RLS-only ADMIN/OWNER gate had
   no test anywhere in the repo.** The functions' own doc comments
   correctly describe `organization_invitations_insert_admin_or_owner`/
   `_update_admin_or_owner` (`20260828130000`) as the enforcement point,
   but nothing exercised a MEMBER actually being refused. Closed by
   adding the `"organization invitations (20260828130000)"` describe
   block to `tests/integration/organizations-isolation.test.ts:1783`
   (live against local Postgres): a MEMBER's INSERT is rejected with an
   error, an ADMIN's INSERT succeeds, a MEMBER's revoke UPDATE affects
   zero rows, and an ADMIN's revoke succeeds.

## Findings — worth flagging, not changed

1. **`updateOrganizationProfile`'s OWNER-only "danger zone" gate lives
   only in a Next.js Server Action** (`app/organization/actions.ts:90`,
   `orgSummary.context.role !== "OWNER"`), not inside the application
   service (`organization-profile.ts`'s `updateOrganizationProfile`
   takes a bare `orgId` and applies no role check at all). This is not
   currently exploitable — the only caller in the codebase is that one
   Server Action, and it does check correctly — but it is inconsistent
   with every ADMIN+/OWNER-gated service elsewhere in this matrix
   (declarations, sharing, emissions, and now `transitionShipmentStatus`
   all check `hasAdminAccess`/role *inside* the service), and this
   codebase has no unit tests anywhere for `app/**/actions.ts` files
   (confirmed: zero `*actions.test.ts` in the repo), so **no test in
   this repo proves the OWNER-only gate holds** at either layer. Not
   fixed in this audit: doing so correctly means changing
   `updateOrganizationProfile`'s signature to take an `OrgContext` (or a
   role parameter) and updating its one caller and its existing unit
   test file (`organization-profile.test.ts`, which currently tests only
   the capability-union behavior) — a real but narrow-looking change
   that this audit chose to name rather than make, since the task's own
   instructions are to close *real* enforcement gaps, and this one does
   not currently have an exploitable path. Recommended follow-up: add
   the `hasAdminAccess`-style check to the service directly and a test
   proving it, mirroring `verifyEmissionData`'s pattern.
2. **`listDeclarations`/`getDeclarationDetail` are ADMIN+-gated only at
   the page-component level** (`app/(importer)/declarations/page.tsx:87`,
   `[id]/page.tsx:116`), not inside the application service, and
   (matching the point above) there is no test — anywhere in this repo
   — proving a MEMBER cannot reach the declarations list/detail data.
   Functionally this is a real, unbypassable gate today: the two page
   components are the only callers of these read services anywhere in
   the codebase (confirmed by search), and a Next.js Server Component's
   data fetch cannot be reached independently of its own render. But the
   same fragility as finding 1 applies — a future server action reusing
   `getDeclarationDetail` for e.g. a downloadable export would inherit
   no protection at all unless it remembered to re-add the same check.
   Not fixed for the same reason as finding 1 (no current exploit path,
   and the correct fix is a signature change this audit's scope asks to
   report rather than retrofit).
3. **Capability enforcement** — see the dedicated section above. Named
   there in full rather than repeated here.

## P10 review response (2026-08-29)

Two independent reviews of the P10 work above (the correctness/TDD
review and this phase's own mandatory authorization review) each found
real gaps this document did not close, or itself introduced. Tracked
here, not silently folded into the sections above, so the response is
as auditable as the original findings.

**Fixed:**

1. **`reactivateMember` reported false success and wrote a fabricated
   `membership.reactivated` audit event when RLS refused the write**
   (BLOCKING, both reviews). `manage-membership.ts`'s `reactivateMember`
   now carries the identical `.select("id")` + zero-rows guard
   `deactivateMember` already had, CAS'd on `deactivated_at` in the
   reverse direction. Proof: `manage-membership.test.ts` (mocked) and
   the new `"membership service-layer CAS guards against RLS-blocked
   writes (P10 review response)"` block in
   `tests/integration/organizations-isolation.test.ts` (live against
   real Postgres, unauthorized caller, asserts zero audit events, then
   asserts the legitimate OWNER path still succeeds and does write one).
2. **The identical gap in `changeMemberRole` and `removeMember`**
   (SHOULD-FIX, both reviews — the reason finding #1 above was possible
   to miss: this matrix's own Proof cells over-claimed what the cited
   test proved). Both now carry the same `.select("id")` + zero-rows
   guard, reporting `PERSIST_FAILED` (this codebase's established
   generic "the write did not happen" reason — see
   `manage-lines.ts`'s `classifyLineWriteError`) rather than `{status:
   "OK"}`. Same live proof as above.
3. **`memberships_update_admin_or_owner`'s WITH CHECK does not pin
   `user_id`, contrary to its own migration header's claim**
   (SHOULD-FIX #5, authorization review) — reproduced live: an ADMIN
   could reassign an existing membership row to an entirely different
   `auth.users` id via a bare UPDATE, with no invitation, no email
   match, no consent, and no audit event. Closed by a new, additive
   migration (`20260829370000_p10_review_response_membership_user_id_immutable.sql`,
   the already-applied `20260828110000` is not edited in place) adding
   a `BEFORE UPDATE` trigger, mirroring the existing
   `app.prevent_org_id_change()` precedent
   (`20260829090000_p4_shipment_tenancy_hardening.sql`) rather than a
   policy rewrite, since RLS's `WITH CHECK` cannot reference a row's
   pre-update value. Live-confirmed both directions: a bare
   `user_id`-reassigning UPDATE now raises, and ordinary role-change /
   deactivation UPDATEs (which never touch `user_id`) are unaffected.
4. **NIT #7 (correctness review): `revokeInvitation` had the same
   missing-`.select()` shape.** Fixed for consistency even though it
   was marked optional — no audit event was ever at stake here (impact
   was a misleading "revoked" toast only), but the fix is one line and
   the same shape as the three above. `invitations.ts`.

**Deliberately not fixed — flagged for an explicit owner decision:**

5. **The last-ACTIVE-OWNER invariant is TypeScript-only; a bare
   PostgREST UPDATE lets a sole OWNER deactivate (or an ADMIN strip)
   the org's last owner, live-confirmed irrecoverable** (SHOULD-FIX #4,
   authorization review). Not fixed in this response. Reversing it
   would mean adding DB-level enforcement of exactly the invariant
   `20260828110000` and `20260829360000` — the latter as recently as
   this same phase — each explicitly and deliberately keep out of SQL,
   for a stated reason (*"duplicating it in a PL/pgSQL trigger... risks
   the two definitions drifting"*) that is a genuine architectural
   position, not an oversight: unlike the `user_id`-immutability fix
   above (a single-fact, nothing-to-count-or-drift-from constraint,
   the same category as the already-precedented `org_id`/
   `shipment_id` triggers), the owner count is exactly the kind of
   cross-row business rule that precedent was written to keep in one
   place. Overriding a twice-made, twice-reaffirmed architecture
   decision is a material architecture change under
   `docs/adr/ADR-0013-review-and-execution-model.md`'s own escalation
   list, not a bug fix inside this phase's contract — so it is reported
   here, as the review itself offered ("a trigger-level guard **or** an
   explicit owner decision to accept"), for a human to decide rather
   than silently reversed.

**Deliberately not fixed — NIT, optional, low impact:**

6. **NIT #6 (authorization review): `deactivateMember` reports
   `ALREADY_DEACTIVATED` to an unauthorized caller** (RLS's zero-row
   result is indistinguishable from a genuine lost race without an
   extra round trip to check the caller's own role). Safe — the write
   still doesn't happen — but the UI copy is misleading about why. Not
   fixed: distinguishing the two cases correctly needs a second query
   this response chose not to add on its own judgment, matching how the
   review itself scored this a NIT rather than a SHOULD-FIX.
   `reactivateMember`'s equivalent `NOT_DEACTIVATED` result inherits the
   same ambiguity, for the same reason.
7. **NIT #8 (authorization review): `deactivated_at` accepts any
   client-supplied timestamp** (no `<= now()` CHECK). Not a bypass —
   only whether the row is null is ever tested — but the Team screen
   could in principle render a future date. Not fixed: a `CHECK
   (deactivated_at <= now())` has its own clock-skew edge cases and
   this is cosmetic, not a security or data-integrity gap.

## P11 review response (2026-08-29)

Postdates this matrix's last edit (P10) by one full review cycle — this
section closes that gap. The P11 mandatory security review
(`4930269`) and this same day's independent P13 re-verification each
found real authorization-relevant gaps, tracked here the same way §P10
review response is.

**Fixed, P11 mandatory review:**

1. **`record_declaration_filed()`'s pre-authorization existence check
   leaked a cross-org oracle** — a caller could distinguish "a real
   declaration id belonging to another org" (`NOT_ADMIN`) from "no such
   declaration at all" (`NOT_FOUND`) purely from the RPC's error
   status, the exact class of finding this matrix exists to catch.
   Closed in `20260829400000_p11_review_declaration_filed_membership_oracle_fix.sql`
   by checking org membership before existence, so both cases now
   return the identical, uninformative `NOT_FOUND`.
2. **`audit_events` had no `event_type` CHECK constraint** — any
   authenticated member could INSERT an arbitrary, unvalidated
   `event_type`/`payload` combination into their own org's audit trail
   via a bare client write (every plain `recordAuditEvent` call site
   goes through RLS, not a `SECURITY DEFINER` RPC). Live-reproduced
   during the review as a fabricated `declaration.filed` row carrying a
   forged `filed_reference`. Closed in
   `20260829430000_p11_review_audit_events_event_type_catalog.sql` with
   a `WITH CHECK` allowlist of every real event type (see
   `docs/architecture/ARCHITECTURE.md`'s event catalog, corrected the
   same day this section was written).
3. **`memberships.org_id` was not immutable** — the same class of gap
