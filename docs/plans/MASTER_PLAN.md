## 1. Executive Summary

Snowkap CBAM is one unified platform serving **two primary experiences**: the **Importer/Declarant workspace** (shipments → classification → regulatory resolution → embedded-emissions calculation → explanation → reporting → declaration preparation) and the **Third-Country Producer/Operator workspace** (installations → production activity → emission data → methodology → evidence → verification → controlled sharing with importers). They share one domain model, one regulatory subsystem, one auth/tenancy foundation, one audit infrastructure, and one design system — and differ in onboarding, navigation, dashboards, workflows, permissions, and reporting. Cross-organization sharing is explicit, granted, revocable, audited, and never weakens tenant isolation (§9).

The foundation already exists and is verified: a pure resolver implementing documented rules R1–R14, a constraint-hardened regulatory schema, and the ACTIVE `2026-definitive-corrected` dataset (12,540 records, checksum-pinned, reconciled 12,540/12,540, verification VALID) with a **29/29-passing** test baseline (§3). What is missing is the product: no UI, server, API, auth, tenancy, CI, or deployment. Phase 0 confirmed one defect in the protected zone (the R7 unlisted-country fallback short-circuited in the adapter — domain resolver correct, adapter-only fix) and a fresh-clone reproducibility gap (§4).

Execution: 14 phases (P0 done). Phase 1 restores correctness and reproducibility in six bounded workstreams (P1-A…P1-F) with zero new dependencies. Phase 2 delivers the branded shell, design system, and a Railway staging walking skeleton. Phases 3–9 build the product spine for both experiences; 10–13 harden, deploy, validate. **Review model**: this master architecture is approved once; Sonnet 5 then executes phases sequentially under their contracts, with Superpowers doing local implementation planning inside phases; humans are engaged only at defined escalation triggers, owner-supplied inputs, production actions, and final sign-off (§34). Regulatory rules are never invented: every regulatory number enters as a versioned, provenance-tracked dataset, and every calculation rule must exist in a formal **calculation-rule register** before implementation (§17).

**Release strategy (§37)**: Importer/Declarant MVP first (complete defaults-based journey: intake → classify → resolve → calculate → explain → report/export). Producer/Operator MVP is the V1 centerpiece (installations → verified emission data → sharing), landing together with importer-side consumption of shared actuals. V1.x adds parameter datasets (markups/benchmarks/certificate prices/exemptions) and liability estimation. Future: public API, SSO, official-submission integration only if a supported channel exists.

## 7. Importer/Declarant Experience

The compliance journey: **onboard** (org + IMPORTER_DECLARANT capability, EORI/declarant status) → **intake** shipments (manual, CSV import; XLSX V1) → **classify** lines (declared CN/TARIC, ISO origin, quantity, route) → **resolve** emissions (default via regulatory resolution with frozen snapshot; actual via own records or producer-shared VERIFIED data) → **calculate** (deterministic engine, trace) → **review** (completeness, stale indicators) → **explain** (full audit chain on any number) → **report/export** (period summaries, CSV/XLSX) → **prepare declaration** (aggregation, completeness gate, package export, record-filed → LOCK). Supporting surfaces: suppliers registry, installations/operators (local or shared-in), emissions library, calculations view, audit history, org settings/team. Navigation, dashboard KPIs (period completeness, unresolved lines, emissions totals), and action queue are importer-specific. Full screen definitions §27.

## 8. Producer/Operator Experience

The supply-side journey: **onboard** (org + PRODUCER_OPERATOR capability) → **register installations** (operator, sites, geography) → **record production activity context** (what the installation produces: CN scope, routes, periods) → **enter emission data** per installation/scope/period with **methodology** (EU method / equivalent / other) → **attach evidence** (documents to Storage, org-scoped) → **verification workflow** (submit → VERIFICATION_PENDING → VERIFIED by named verifier | REJECTED with reason; approval actions audited) → **share with importers** (issue/accept grants, see §9) → **monitor shared-data status** (which importer orgs see which installations, grant states, last-access) → **emissions history** (versions, supersessions) → **activity/audit** and **settings/team**. The producer dashboard centers on: installations coverage, datasets by verification state, expiring/revoked grants, importer requests. Producer data entry is the authoritative source (`OPERATOR_PROVIDED`); importers consuming it never edit it. Full screen definitions §27.

## 9. Shared Data / Relationship Model

**Problem**: one producer's verified installation/emissions data must be reusable by multiple authorized importer organizations without ever weakening tenant isolation.

**Options compared**: (a) *ad-hoc share token/link* — lowest friction, weakest identity/audit; rejected as the primary mechanism (kept only as the bootstrap invitation transport). (b) *blanket organization relationship* (partner orgs see everything) — too coarse; over-shares future installations. (c) **installation-scoped grants under an organization relationship — CHOSEN**: explicit, minimal-scope, auditable, revocable.

**Chosen design**: a producer org creates a **SharingGrant** {grantor_org, grantee_org, installation_id, scope: that installation's ACTIVE **VERIFIED** EmissionData (+ installation profile), status INVITED→ACTIVE→REVOKED|EXPIRED, optional expiry, created_by}. Bootstrap: if the importer org isn't known, the grant is issued against an email invitation (signed, expiring token) that resolves to the grantee org on acceptance; either side may initiate a request (importer requests access; producer approves — approval is the grant). **Authorization & isolation**: grants confer **read-only** access, enforced by both walls — application services check grant scope, and RLS SELECT policies on `installations`/`emission_data` admit grantee members via a `security definer` helper (`app.user_shared_installation_ids()`) driven by the grants table; no write policy ever crosses orgs; DRAFT/REJECTED/DISCARDED producer data is never visible to grantees. **Revocation/expiry**: immediately ends future reads; nothing historical is clawed back because determinations hold frozen copies (§16) — historical calculations continue to use exactly the snapshot they froze. **Updates/versioning**: when the producer supersedes a dataset, grantees see the new ACTIVE version; importer-side lines show a stale-data indicator, and re-determination is an explicit, audited importer action — never automatic. **Ownership**: producer data remains producer-owned; the importer's determination snapshot is importer-owned. **Audit**: grant lifecycle events (invited/accepted/revoked/expired), and consumption events (determination-from-shared-data) recorded on both orgs' audit streams; the producer's shared-data status screen shows grants + last-used. Standing two-org isolation tests extend to three-party (producer, grantee importer, stranger org) adversarial cases from P7.

## 13. Tenancy / Security (isolation model)

**Two walls, always both.** Wall 1 — application: `OrgContext` on every service; ports org-scoped by signature; capability + role checks (matrix §14). Wall 2 — Postgres RLS on every product table from creation, enforced end-to-end because product requests use the user-scoped client. Cross-org **sharing** is the only sanctioned crossing, read-only, grant-scoped, dual-wall enforced (§9). Service-role confined to system jobs + regulatory adapter, server-only, CI-gated. **Standing tests, not assumptions**: two-org isolation suite from P3 on every new port/policy; three-party sharing adversarial cases from P7 (stranger org sees nothing; revoked grantee loses reads; grantee never writes); P11 adversarial pass (IDOR probes on handlers, storage path probing, service misuse). ## 15. Regulatory Architecture

Separation preserved verbatim: **Repository** retrieves candidates (ACTIVE dataset, requested country + fallback territory, exact normalized code, routes — post-R7-fix the fallback territory's candidates return even when the requested country is unlisted); **Domain resolver** makes the regulatory decision (untouched; zero-diff guarantee in P1 outside the two approved additive changes, which do not touch `resolve-default-value.ts`); **Application** orchestrates. ISO→regulatory country mapping via `RegulatoryCountryMapper` (P5): ISO→dataset name from `countries` iso2/iso3; outcomes `MAPPED | UNLISTED` recorded in the snapshot; unlisted flows to the fallback territory by R7. CN/TARIC: declared code stored, normalized for resolution; specificity stays in the resolver. Routes: product stores `{name, indicator}`, resolver receives the indicator (documented contract, ADR-0010). Statuses/reasons/trace preserved verbatim into snapshots and UI.

**Regime versioning (owner directive)**: the architecture serves the **current definitive CBAM regime** and future amendments through versioned datasets alone. Three categories are kept explicit everywhere: **CURRENT VERIFIED DATA** (the ACTIVE default-values dataset — the only regulatory data verified in-repo today), **FUTURE REGULATORY DATA** (markups, benchmarks, certificate prices, exemption thresholds, declaration rounding rules — enter as new dataset types through source registration → versioned DRAFT load → verification gate → activation migration; **never hardcoded even when the values are publicly known today**), and **APPLICATION LOGIC** (workflow, persistence, UI — carries no regulatory numbers). Supersession never mutates rows; resolution reads only the ACTIVE dataset of a type; history is safe via snapshots.

## 16. Provenance

Every regulatory value remains traceable to source → dataset → version → country → trade code → route → source record. Mechanisms: dataset-level (`regulatory_sources` document/version/URL; `regulatory_datasets` checksum/version/status; `dataset_version` added to `RegulatoryRecord` in P1-C so consumers can record it without a second query); record-level (source sheet/row/raw trade code/raw values/route indicator carried into the domain record); determination-level (**frozen snapshots**: `RegulatoryResolutionSnapshot` = dataset id+version, resolved_at, reason, record identity, all three values with statuses, unit, full R12 trace; `ActualEmissionSnapshot` = emission-data identity+version, values, methodology, verification state + verifier, evidence refs, owning org, sharing-grant reference when consumed across orgs); calculation-level (engine_version + parameter-dataset ids/versions + step traces, append-only). A newer ACTIVE dataset, a superseded emission record, or a revoked grant can never alter stored history; any historical result is re-derivable from its snapshots alone.

## 17. Calculation Engine

Dedicated pure domain module (`src/domain/calculations/`) — never in repositories, SQL, adapters, or UI. Pipeline: **Shipment → Classification → Regulatory resolution → Default/actual determination → Embedded emissions → CBAM-specific calculations → Result.**

**Calculation-Rule Register (mandatory precondition — owner directive).** Before the engine is implemented (P6 precondition), `docs/regulatory/CALCULATION_RULE_REGISTER.md` is authored and reviewed. Every implemented rule carries: rule ID · authoritative regulation · implementing/delegated act where applicable · article/annex/section · effective period · applicability · inputs · units · formula · rounding rule · exceptions · authoritative source URL/citation · golden regression fixture — and a classification: **REGULATORY FACT** / **APPLICATION DESIGN DECISION** / **FUTURE-DEFERRED**. **No regulatory formula is implemented from inference alone**; a rule absent from the register cannot be coded. The register is versioned in-repo and every engine trace step cites its rule ID.

Component classification (governs the register's initial content): embedded-emissions structure (quantity × specific embedded emissions; MWh basis for electricity) — FACT, encoded from Reg (EU) 2023/956 Annex IV + implementing acts with citations; default specific values — CURRENT VERIFIED DATA via snapshot; actual specific values — FACT (method constraints) + DESIGN (workflow §18); markup on defaults, benchmark/free-allocation adjustment, certificate price (ETS-auction-linked), exemption/de-minimis thresholds — FACTS whose **data is FUTURE-DEFERRED datasets**; precision (Decimal 40 HALF_UP, full precision persisted, rounding only at presentation/declaration; declaration rounding is a FACT to extract before P9) — DESIGN; units (tonnes canonical, kg→t exact, MWh for electricity, all else rejected explicitly) — DESIGN; engine versioning/trace/statuses — DESIGN.

**Determinism**: `calculate(inputs, parameters) → outcome` is pure (no clock/env/I/O); inputs = quantity + determination snapshot; parameters = ACTIVE parameter-dataset rows identified by id+version in the result; trace steps `{step, rule_ref, formula, inputs, value}`; `engine_version` bumped on any behavioral change with golden fixtures per version; same inputs + version ⇒ byte-identical output, re-provable on demand (§21).

**Parameter safety (owner directive)**: the product cleanly separates **embedded-emissions calculation** (computable today) from **certificate/liability estimation**, **exemption/de-minimis decisions**, and any other regulatory conclusion. When a required parameter dataset is unavailable: never invent, never substitute — return explicit states (`INPUT_UNRESOLVED`, `VALUE_UNAVAILABLE`, `REFERENCE_REQUIRED_UNRESOLVED`, `NOT_APPLICABLE`, `AMBIGUOUS_INPUT`, `PARAMETER_DATASET_UNAVAILABLE`, `UNIT_UNSUPPORTED`), explain the limitation in the UI, and **never present the downstream result as a complete compliance or liability conclusion** (estimates are labeled, gaps are named, and reports carry the same caveats).

## 18. Actual / Default Emissions

DEFAULT and ACTUAL are never silently mixed; the method travels into every result, report, and export. **Actual workflow** (P7): operator + installation registered (producer-owned, or importer-entered for off-platform producers with provenance marked) → EmissionData per installation/CN-scope/period with methodology → evidence attached → verification advanced (VERIFIED requires named verifier; REJECTED requires reason; approvals audited) → only **ACTIVE + VERIFIED** data is eligible for determinations → supersession creates a new version; affected importer lines show stale indicators; **re-determination is an explicit audited action, never automatic**. Invalid/rejected/unresolved actual data is **never silently replaced with defaults** — falling back to DEFAULT is an explicit user action with an audit event. Selection policy ("prefer actual when a VERIFIED dataset covers the line") is an org-level setting implemented as an explicit audited selection step. Sharing-consumed actuals carry the grant reference in the snapshot (§16).

## 19. Shipment Architecture

Lifecycle `DRAFT → validation → classification → emission determination → calculation → review → READY → declaration inclusion → LOCKED`, with `VOID` from DRAFT/READY, and READY→DRAFT reopen. Pure `transitionShipment` returns enumerated rejections (e.g. `LINE_INCOMPLETE`, `ALREADY_LOCKED`). Editability: header + lines mutable in DRAFT (and via reopen); LOCKED/VOID immutable including lines — enforced app-side and by RLS update policies checking parent status. Line completeness = declared code + origin + quantity + determination. Recalculation: allowed until LOCKED; results append (never overwrite); stale indicators when inputs changed after the last calculation. Incomplete data blocks READY with an exact defect list, never silent defaults. Import (§10) creates DRAFT shipments only. Every transition, determination, calculation, lock, and void emits audit events; historical reproduction guaranteed by §16.

## 20. Classification

Product-side, declarative (no ML confidence — deliberately): the importer declares the CN/TARIC code as imported. Model: `cn_code` (8/10 digits) + level; validation = format (regex + level consistency), existence against `cbam_goods` (assistive searchable combobox over the 283 goods), origin ISO country, quantity + unit fit (MWh only for electricity goods), route picker showing names while storing `{name, indicator}`. Outcomes are explicit: `VALID`, `UNSUPPORTED_CODE` (not a CBAM good — with nearest-match assistance, never auto-substitution), `INVALID_FORMAT`, `AMBIGUOUS` (user must pick level/code — the system never guesses). Classification explanation states what was validated against which goods-list entry. Regulatory truth is not duplicated: the goods list, levels, and specificity live in the regulatory subsystem; the product stores only the declaration and validation outcome.

## 21. Auditability

Every material result explains: **Input → Classification → Country → Trade code → Route → Regulatory dataset → Selected record → Fallback → Emission determination → Calculation → Result** — via the frozen snapshots (§16), append-only calculation results, and the AuditEvent stream (schema §6: actor, organization, entity/aggregate ref, action event_type, correlation ID, timestamp; immutable history via revoked grants + absent update/delete policies; catalog grows per phase and includes **sharing/access events**: grant invited/accepted/revoked/expired, shared-data consumed). Correlation IDs thread request → logs → audit events → calculation rows. Regulatory traces (R12) and calculation traces render in the explanation panel, reachable from every number via a "Why?" affordance. **Reproduction proof** (P8): CI test + on-demand admin check recomputing stored results from their snapshots with the recorded engine_version, asserting byte-equality. Retention indefinite; audit export available; `pnpm regulatory:verify` remains the dataset-level audit anchor.

## 22. Reporting / Declaration

Strict layering: **internal calculations** → **reporting** (period summaries by CN/country/route/method, determination-mix, drill-through) → **export** (CSV + XLSX with full provenance columns — dataset versions, reasons, engine version; branded PDF V1.x) → **declaration preparation** (annual aggregation, blocking completeness gate, exportable declaration package whose field mapping to the official format is a P9 precondition (§41), record-filed workflow: timestamp + reference + filed snapshot + LOCK member shipments; amendments as new versions) → **official filing: out of scope** — no registry submission capability is claimed without a supported official integration; the authorised declarant files themselves, Snowkap prepares, explains, archives, and records. First production scope: reporting screen + CSV/XLSX export (importer MVP); declaration preparation + recording in V1.

## 40. Risks

1. **Regulatory misinterpretation** — facts-as-datasets + calculation-rule register + citation duty + regulatory reviews + never-invent rule + verify gates + frozen snapshots.
2. **Tenancy/RLS/sharing gaps** — dual-wall design, standing two-org + three-party adversarial suites, Opus reviews (P3/P7/P10/P11).
3. **Calculation defects** — register-gated implementation, pure deterministic engine, golden fixtures per engine_version, reproduction proofs, Opus review.
4. **Protected-zone regression** — additive-only, resolver zero-diff guarantee, one-commit-per-change, verify gate after each.
5. **Parameter-dataset availability** — inert stages + explicit unavailable states keep MVP shippable without false liability numbers.
6. **UI scope creep** — design system + contracts + §25's bounded direction.
7. **Toolchain novelty** (TS7/Tailwind4/Next current) — P2 spike; domain unaffected.
8. **Single-maintainer bus factor** — docs/ADR/runbook discipline; this plan in-repo.
9. **Supabase coupling** — ports isolate; exportable SQL/storage; revisit criteria documented.
10. **Timeline realism** — MVP cut (§37) is the pressure valve, never quality.

## 42. Non-Goals

## 43. Rollback Strategy

**Code**: feature branches, gated merges, `git revert`; protected-zone changes one-commit-each, independently revertible, verify-gate re-run proving data untouched. **Migrations**: forward-only; staging-first; production only via the gated runbook; recovery = roll-forward or PITR; restore drill tested (P11); early phases additive so abort stays cheap; destructive changes only through §42. **Deployments**: Railway previous-build redeploy (rehearsed P12); health-gated promotion; staging always one step ahead. **Data**: append-only designs (audit, calculations, snapshots, supersession chains, grants) make undo a status flip, not a delete; regulatory datasets roll back by activation-flip migration, never row mutation; revocation never rewrites history. **Phase level**: every phase lands mergeable-and-revertible; no phase entangles a prior accepted surface without its own contract.
