# EU-ORIGIN SCOPE — DECISION BRIEF

**Question for the owner:** may a shipment line declaring an EU member state as origin be determined, calculated, reported and filed by this platform — and if not, how does in-scope/out-of-scope enter the system as authoritative data?

**Evidence rule used throughout:** ESTABLISHED = written in this repo with a citation · ABSENT = repo is silent · INFERRED = a reading, not authoritative. Three findings below rest on a live read-only database probe rather than repo text; they are marked `[live probe — not repo-citable]`. No outside regulatory knowledge is used: where the brief says "CBAM applies only to third-country goods," that is quoted as a *repo statement* (`docs/plans/MASTER_PLAN.md:371`), not asserted as law.

## A. Current EU-origin behaviour

The chain, link by link. Each link is separately ESTABLISHED; the composition is INFERRED (traced in source, not executed).

1. **Intake accepts it.** `parseCountryCode` tests `/^[A-Z]{2}$/` only (`src/domain/shared/country.ts:20-36`); the DB carries the identical check (`supabase/migrations/20260828150000_p4_shipment_intake_schema.sql:301-302`); `addLine`/`updateLine` reject only on shape (`src/application/shipments/manage-lines.ts:267-277`, `:424-434`); the Server Action schema is `z.string().min(1)` (`app/(importer)/shipments/[id]/actions.ts:232-233`), uppercased at `:473`; the UI field is free text, `maxLength={2}`, `placeholder="ISO code, e.g. CN"` (`app/(importer)/shipments/[id]/add-line-form.tsx:144-154`). `DE` is accepted at every layer exactly as `CN`. **[ESTABLISHED]**

2. **Mapping returns UNLISTED.** `mapCountry` selects from `countries` on `iso2` + `country_type='COUNTRY'` + `active=true`; a null row returns `{status:"UNLISTED"}` (`src/infrastructure/regulatory/supabase-regulatory-repository.ts:988-1035`). The port's doc comment says this is "expected and common for EU member states, since CBAM's default-value dataset only publishes country-specific values for non-EU trading partners" (`src/infrastructure/regulatory/regulatory-repository.ts:88-92`). **[ESTABLISHED]**

3. **Why EU states are absent.** `countries` is seeded solely from the dataset's `origin_country_name` values (`scripts/regulatory/load-definitive-default-values.py:1185-1293`) through a hardcoded `COUNTRY_ISO` map (`:97-222`) that raises on unknown names (`:384-426`) and contains no EU member state; `supabase/seed.sql` seeds no countries; no migration inserts into `countries`. The canonical processed dataset holds 12,540 records / 122 distinct geographies (121 countries + `_Other Countries and Territorie`), none an EU member state (`data/processed/default-emission-values-definitive.json`; corroborated at `docs/regulatory/REGULATORY_REFERENCE_DATA_MUTATION_DECISION_MEMO.md:87`, `docs/plans/MASTER_PLAN.md:36`, `docs/runbooks/BACKUP_RESTORE.md:296`). **[ESTABLISHED]** *Caveat:* the live table's contents are not repo-citable. `DE → UNLISTED` is asserted by an integration test (`tests/integration/regulatory-repository.test.ts:325-343`), which is credential-gated by `describe.skipIf(!hasSupabaseEnvironment)` at `:302`; the other 26 member states rest on the loader-plus-dataset chain, not on a test.

4. **A synthetic country name is handed to the protected resolver.** `resolutionCountryName` returns `` `(unlisted origin: ${isoCode})` `` for any non-MAPPED outcome (`src/application/emissions/resolve-line-emissions.ts:159-166`, template at `:165`), documented as deliberately non-colliding so the resolver's own fallback runs (`:147-158`). It is passed as `origin_country_name` to both the candidate fetch and the resolver (`:203-227`). *(The literal string `(unlisted origin: DE)` does not appear in the repo; `DE` is an illustration.)* **[ESTABLISHED]**

5. **The adapter does not pre-filter.** `findActiveDefaultEmissionCandidates` fetches `[requestedName, "_Other Countries and Territorie"]` (`supabase-regulatory-repository.ts:303-325`); the comment at `:384-394` states this is R7 clause 1 and that "this adapter's job is only to fetch them, never to pre-filter by whether the requested country happens to be known." It throws only if *neither* name resolves (`:415-422`) — unreachable while the fallback row exists (`:403-414`). **[ESTABLISHED]**

6. **The resolver runs R7 clause 1.** Zero records for the synthetic name → `NO_COUNTRY_MATCH`, `hasExactMatch:false` (`src/domain/regulatory/resolve-default-value.ts:154-173`); the exact-match early return at `:777-782` is skipped; the fallback block at `:792-839` re-resolves against `_Other Countries and Territorie` and overrides the reason to `OTHER_COUNTRIES_FALLBACK` (`:815-831`). **This path is identical for a genuine unlisted third country and for a well-formed non-country code** — `mapCountry("ZZ")` is also UNLISTED (`tests/integration/regulatory-repository.test.ts:345-357`). **[ESTABLISHED]**

7. **A real determination is persisted.** `buildResolutionSnapshot` returns non-null only for `RESOLVED` (`src/domain/emissions/build-resolution-snapshot.ts:32-34`) and copies reason (`:43`), `country_mapping` verbatim (`:44`), `record_identity.origin_country_name` = the Other-Countries row (`:50`) and the three values (`:54-58`); the service writes `{method:"DEFAULT", resolution}` to `shipment_lines.emission_determination` (`resolve-line-emissions.ts:244-248`, `:260-284`). The result is structurally indistinguishable from a legitimate third-country determination except that `country_mapping.status` is `UNLISTED`. **[ESTABLISHED]**

8. **The DB forgery validator (v10, current head) accepts it.** The UNLISTED arm requires only (a) the declared origin is absent from `public.countries` (`supabase/migrations/20260902140000_p13_review_shipment_line_determination_validator_v10.sql:385-389`), (b) the matched record is `_Other Countries and Territorie` (`:391-393`), (c) reason is `OTHER_COUNTRIES_FALLBACK` (`:395-397`). Condition (a) is exactly why an EU code was UNLISTED. The migration's own matrix records "B2 genuinely UNLISTED origin  True" (`:56`). Enforced by the BEFORE INSERT OR UPDATE trigger created at `20260829580000_..._v3.sql:637-640`. **[ESTABLISHED]** `[live probe]` confirmed v10 is the installed function body and the trigger is enabled.

9. **The uniqueness rule never blocks it.** v10's B1 check requires exactly one usable Other-Countries candidate per trade code (`v10:463-480`). `[live probe — not repo-citable]` 283 Other-Territories rows in the ACTIVE dataset, 260 with `total_status='AVAILABLE'`, and grouping those 260 by `source_trade_code` yields `cnt=1` for all 260. Practical consequence: an EU-origin line declaring any of the 260 codes gets a persisted, validator-accepted number today.

10. **The audit trail sees it but nothing acts on it.** `recordAuditEvent` carries `country_mapping_status` (`resolve-line-emissions.ts:335-350`) on `emission_determination.set` (`:396`) / `.redetermined` (`:432`). It is a record, not a gate. **[ESTABLISHED]**

11. **This path is two days old.** v5..v8 routed UNLISTED into the MAPPED comparison against an absent key, so "every UNLISTED determination was rejected, and R7 clause 1's entire persistence path has been dead since v5" (`v10:369-379`; `20260902090000_..._v9.sql:53-64`). v9 (2026-09-02) reopened it deliberately: "this migration does make such determinations persistable again, where the B2 defect was incidentally preventing them… OWNER DECISION REQUIRED before real declarant use" (`v9:68-83`). P13 §52.3 records production held **0 rows** in the UNLISTED state at the time (`docs/plans/P13_RELEASE_READINESS_REPORT.md:3505-3512`) — an opened path, not existing bad data. **[ESTABLISHED]**

12. **A second determination path ignores origin entirely.** `determine-from-actual-data.ts:125-137`: "this determination path never touches origin_country/production_route_indicator." Its gates are org ownership, CN-scope coverage, dataset ACTIVE+VERIFIED, evidence presence — none geographic (`:146-153`). **[ESTABLISHED]**

13. **The gap is already recorded as open and escalated** in the domain type itself (`src/domain/emissions/types.ts:41-49`, "KNOWN OPEN GAP … a deliberate, documented escalation"), the master plan (`MASTER_PLAN.md:371`, "escalate, do not patch", due "before default-value resolution is relied on for real declarations"), the memo (`memo:254-282`, "OPEN, NOT DECIDED HERE"), the v9 migration header (`v9:70-80`), and P13 (`:2349-2359`, `:3905-3906`). **[ESTABLISHED]**

## B. What the authoritative source explicitly requires

**One scope-adjacent rule in this repo has been verified against primary legal text.** `docs/regulatory/R7_R9_COUNTRY_FALLBACK_DECISION_MEMO.md:329-376` records fetching CELEX:32025R2621 and CELEX:32026R1740 "directly, twice… in a real browser session, not inferred," and quotes Annex I verbatim (`:343-350`): *"Where a country or territory is not explicitly listed, the default value … from the table 'Other countries and territories' needs to be selected. Where a country or territory is explicitly listed but no value is provided or the relevant field shows '–', the default value … needs to be selected."* Both readings identical. **[ESTABLISHED]**
*Caveat the memo itself records:* §13 (`:537-573`) concedes the code fix and the memo's resolution came from one continuous session 46 seconds apart "with no distinct external sign-off visible in the repository's own history," and asks the owner to re-read the two URLs before treating it as final.

**R7 as transcribed** (`docs/architecture/REGULATORY_RESOLUTION_RULES.md:107-119`): clause 1 triggers on "not explicitly listed"; clause 2 on listed-but-blank/"–"; "This fallback is applied per regulatory good/value, not as a blanket replacement of the entire country's table" (`:118-119`). **No third-country, non-EU, or in-scope qualifier appears** in the rule, its heading, or its surrounding text. **[ESTABLISHED]**

**R9** (`:134-143`): `UNAVAILABLE` is not zero; it triggers the R7 fallback attempt; if the fallback is also unavailable, resolution remains unresolved. It governs value *availability*. That it says nothing about *applicability* is ABSENT (silence) + INFERRED (the conclusion drawn from that silence).

**R13** (`:177-188`): "The resolver may only apply rules defined in this document." The document's complete set is R1–R14 plus a `production_route` contract note (`:28-229`); none is a scope, applicability, exemption, or origin-eligibility rule; the word "scope" does not appear in the file. **[ESTABLISHED]** *Scope caution:* R13 binds **the resolver**, not the platform; R14 (`:189-194`) expressly places other CBAM calculations outside it. Using R13 to argue scope logic is forbidden platform-wide would be INFERRED overreach.

**Calculation rule register** (`docs/regulatory/CALCULATION_RULE_REGISTER.md`): nine rules, RULE-EE-001…009 (`:55, 223, 304, 382, 412, 445, 565, 628, 676`), all embedded-emissions computation. Citations must be "never inferred from general CBAM knowledge, training data, or analogy" (`:7-8`). "A rule absent from this register cannot be coded" (`:10`) — but `:5-7` scopes the register to `src/domain/calculations/` ("no register, no engine"); whether it also gates a scope check outside the engine is **INFERRED**, and the repo's own note on this gap invokes the facts-as-datasets rule instead (`src/domain/emissions/types.ts:46-49`).

**Exemptions are named but never ingested.** RULE-EE-003's inputs (`register:316-318`) and its verbatim IR 2025/2547 Annex II A.1(4) quote (`:334-337`) refer to "third countries and territories that are not exempted pursuant to point 1 of Annex III to Regulation (EU) 2023/956." **"Annex III" appears exactly twice in this repo, both here; its content is nowhere** — not transcribed, not in `data/`, not in any dataset. This is the single strongest in-repo signal that a regulatory scope/exemption instrument exists and has not been ingested. **[ESTABLISHED]**

**Electricity conditions** (RULE-EE-007/008, `register:565-605`, `:650-660`) quote Annex IV point 5 verbatim, including "a producer of electricity located in a third country" and "directly connected to the Union transmission system" — conditions for actual-vs-default electricity values, expressly not implemented by engine code (`:584`). They establish nothing about which origins are in CBAM scope. **[ESTABLISHED]**

## C. What it does NOT establish

- **The premise "CBAM does not apply to EU-origin goods" is asserted flatly, without citation, in five places:** `MASTER_PLAN.md:371` ("CBAM applies only to goods imported from third countries"), `DETERMINATION_VALIDATOR_SEMANTICS_DECISION_MEMO.md:258`, `P13:2353`, and — correcting any "planning prose only" framing — in **code** at `src/domain/emissions/types.ts:41-49` and in a **migration comment** at `v9:70-80`. None carries an article reference, quoted text, or a record of a primary-source read. As a repo statement: ESTABLISHED. **As a sourced regulatory rule: ABSENT.**
- **Nothing records that this claim was ever checked against a primary source** — no attempted read, no failed-fetch record, no URL, no "needs verifying" note about the claim itself (only about what to do with it). Contrast the R7/R9 memo, which devotes `:213-253` to what was *not* read and why, and `:329-376` to the eventual direct read. **[ABSENT]**
- **Whether the "Other countries and territories" table is a residual-*third-country* table or a residual-*any-country* table is nowhere stated.** The verbatim primary text says "not explicitly listed" with no qualifier (`R7_R9 memo:343-350`); the schema pins the row's name to the literal workbook header (`DATABASE_SCHEMA.md:326-333`). Both readings are consistent with every piece of text this repo holds. **This is the hinge of the decision. [ABSENT]**
- **No definition of "EU origin", "Union origin", or "customs territory of the Union", and no rule for how a good's origin is determined** — non-preferential customs origin? country of production? country of dispatch? the declarant's asserted value? "Customs territory" appears once, undefined, in a role description (`docs/architecture/DOMAIN_MODEL.md:22`). No treatment of EU territories with special customs status, of EU-origin goods returning after processing abroad, or of any territory-vs-member-state distinction. **[ABSENT]**
- **No in-scope/out-of-scope dataset, column, rule, or register entry exists for any dimension.** `regulatory_datasets.dataset_type` anticipates `COUNTRIES` and `EXEMPTIONS` (`DATABASE_SCHEMA.md:286`) but no such row, ingestion script, content schema, or register entry exists; only `DEFAULT_EMISSION_VALUES` is ever referenced (11 sites). `countries` has no scope attribute — `country_type ∈ {COUNTRY, OTHER_TERRITORIES}`, existing solely so the fallback geography can be represented (`DATABASE_SCHEMA.md:309-336`, `:57`); `active` is a row-lifecycle flag. **There is no column an in-scope/out-of-scope fact could be written to today without a schema change. [ABSENT]**
- **`cbam_goods` (283 rows) is nowhere described as the Annex I scope list** — it is the classification hierarchy derived from the default-values workbook (`DATABASE_SCHEMA.md:357-388`). `UNSUPPORTED_CODE` (`MASTER_PLAN.md:164`) is existence-against-`cbam_goods` validation, never given a regulatory citation tying that table to Annex I. **[ESTABLISHED that it is not so described]**
- **Exemption/de-minimis thresholds are explicitly FUTURE-DEFERRED and unregistered** (`register:834-851`, `:843`), and "None of the above may be implemented from inference" (`:849-851`). No threshold value, unit, or test exists. **[ESTABLISHED as a deferral, ABSENT as a rule]**
- **No ADR addresses CBAM scope, EU origin, or applicability** (18 ADRs; only unrelated uses of "scope"). **[ABSENT]**
- **The repo is silent on what should happen to an out-of-scope line, even hypothetically.** The open question is framed only as "whether an EU-origin line should be determinable at all" (`memo:277-280`). No source states whether such a line should be rejected at classification, accepted but marked NOT_APPLICABLE, determined-and-flagged, excluded from period totals, or blocked at the declaration gate. Neither the classification vocabulary (`MASTER_PLAN.md:164`) nor `CountryMappingOutcome` (`types.ts:51-53`) has an out-of-scope member. **[ABSENT]**
- **No EU country list exists anywhere in the repo, in any form** — and introducing a hardcoded one is doubly forbidden: `memo:270` rejects "Fix B2, exclude EU origins with a country list" as "exactly the invented regulatory scope CLAUDE.md forbids. In-scope/out-of-scope must enter as a versioned dataset"; `MASTER_PLAN.md:371` requires "an authoritative, versioned in-scope/out-of-scope country dataset per the facts-as-datasets rule, not a hardcoded EU list"; `CLAUDE.md:56-61` is the governing rule. **[ABSENT + prohibition ESTABLISHED]**

**INFERRED, flagged as non-authoritative:** read literally, R7 as transcribed *does* apply to an EU origin — its trigger is "not explicitly listed," which an absent member state satisfies, and the rule carries no eligibility precondition. The conflict here is therefore **not** resolver-versus-rule (as R7 clause 2 was); it is that the rule as transcribed has no scope precondition at all, and whether one was meant to exist *upstream of it* is unanswered in this repo. Note that R7 clause 1 and the resolver both contain country-level branch points (`resolve-default-value.ts:722-726`, `:774-775`, `:793-794`), so any claim that "there is nowhere a scope check could sit" is not supportable.

**Correction to carry:** "no scope concept exists anywhere in this codebase" is too broad. `cn_scope` is an implemented, unrelated **goods-coverage** scope concept (`src/domain/emissions/types.ts:163`; `20260829230000_p7b_emission_data_schema.sql:168`; `v9:116, 181-184`). Do not conflate it with territorial scope.
