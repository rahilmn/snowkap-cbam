# ADR-0009: Identity — branded UUID string IDs, generated in the application layer

## Status

Accepted

## Context

TypeScript's structural typing means any `string` can stand in for any
other `string` — nothing stops an `OrganizationId` from being passed
where a `ShipmentId` is expected, a mistake that would only surface at
runtime (or in production) as a foreign-key mismatch. The product
domain introduces many ID-typed fields across many aggregates
(`OrganizationId`, `ShipmentId`, `EmissionDataId`, `SharingGrantId`,
...), making this exactly the kind of mistake that becomes likely at
scale.

## Decision

Every aggregate ID is a **branded** string type via a generic helper
(`Brand<T, B>`, `src/domain/shared/ids.ts`): plain strings at runtime
(no wrapper object, no serialization concern), but distinct,
non-interchangeable types at compile time. IDs are UUIDs, generated by
the **application layer** (`crypto.randomUUID()`, injectable for
tests) at the moment a new aggregate is created — not left to a
database `DEFAULT gen_random_uuid()` to invent silently, though the
database default remains as a backstop for direct-SQL paths (e.g. the
regulatory pipeline). Domain code never generates its own IDs; it
receives them as already-assigned values.

## Alternatives considered

- Plain unbranded `string` IDs — rejected: this is precisely the
  mistake-class branding exists to prevent, and the regulatory domain's
  own precedent (opaque `RegulatoryRecord.dataset_id`, discovered in
  Phase 0 to be "a UUID from the DB but a slug in canonical JSON" — two
  identity kinds silently sharing one field) is a cautionary example of
  what happens without it.
- A wrapper class/object per ID type (`class OrganizationId { constructor(public readonly value: string) {} }`)
  — rejected: adds runtime overhead and object-identity comparison
  pitfalls (`new OrganizationId("x") !== new OrganizationId("x")`) for
  no benefit over a compile-time-only brand.
- Database-generated IDs only (no application-layer generation) —
  rejected: an application-generated ID lets a service reference an
  aggregate's ID (e.g. for an audit event or a related record) *before*
  the insert completes, and makes idempotent-create patterns
  (client-supplied ID de-duplication) straightforward later.

## Consequences

Every new ID type is added to `src/domain/shared/ids.ts` rather than
declared ad hoc per aggregate module, so the full ID vocabulary stays
in one place.
